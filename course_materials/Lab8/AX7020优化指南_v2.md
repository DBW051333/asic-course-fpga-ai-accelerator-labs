### P0：以软件候选为新对照，完成有边界的热点剖析

建议新目录 `/home/ding/vivado_project/Lab8_AX7020_trials/ps_api_v2`，直接父 ID 记录为 `lab8_ax7020_ps_api_v1`，源指定基线仍为 `lab8_128_resource_v1`。先保存父版驱动、硬件和模型身份；沿用已经验证的 bit/hwh，开展软件分析。

第一目标仍建议选择 **batch N=42 完整 API 中位数再降至少5%**；scalar N=1、batch N=128、全部既有批量点的中位数/P95为并行报告项。若需求改为单样本低延迟，在实验开始时明确主指标，不在结果出来后挑选收益最大的 N。

将候选的开销拆为：响应拷贝、类别/分数/padding检查、MMIO统计、结果构造；DMA启动、等待循环、完成处理及缓存操作。先用剖析确认调用数量与热点，再对选中的局部做微基准。插桩用于归因，最后验收使用相同的无新增细分插桩外层计时。

建议输出一张“当前热点—可消除工作—估计可省μs—接口代价”的表。不要凭约530 μs解析时间就假定全部来自MMIO，也不要凭约936 μs DMA窗口就假定换中断能全部消除。

### P1：优先评估批量响应解析与统计，保持接口语义

batch N=42 的响应仅336字节，当前仍有约529.769 μs解析/统计开销；N=128响应1024字节，对应约595.087 μs。这提示固定调用成本值得检查，但不能据此断定具体函数占比。

从 [infer_batch 实现](/home/ding/vivado_project/Lab8_AX7020_trials/ps_api_v1/ps/lab8_driver.py) 出发，小原型可评估：减少临时布尔数组和重复遍历、合并合法性检查、减少冗余结果构造/寄存器访问。应先拆分时间，再决定用NumPy表达式、普通循环还是局部原生实现；不能假定Python循环或大范围C重写必然更快。

以当前N=42为参照，完整API再降5%需省约87.497 μs；若全部来自解析阶段，需要该阶段约16.5%的净改善。假设解析缩短20%，粗略整体潜力约6.05%，足以进入小原型，但尚不是已实现收益。

保留实际接收长度、类别范围、signed-score/class一致性、padding、硬件字节计数与所有现有返回字段。返回数组继续具备快照生命周期；不能把独立拷贝改为下次DMA会覆盖的视图。旧版的 `.any()` 和普通ndarray视图已采用，下一轮收益必须来自新增变化。

若剖析证明保持现有接口难以达标，轻量接口可另行提出，但必须与完整接口分别报告；删统计、删校验或改返回字段产生的变化，不作为同语义完整API加速。

### P2：DMA调用、状态读取与完成处理

DMA窗口占N=42完整API约53.46%，约缩短9.35%才可单独贡献整体5%；作为示例，缩短15%对应整体约8.02%的粗略潜力。scalar路径的优先级更高。实际能消除多少需由候选驱动及板上安装的PYNQ源码确认。

当前 `_wait_dma()` 逐次访问两路 `error`、`idle`，确认完成后再调用 `wait()`。可以研究每轮读取一次通道状态并同时判断错误/完成，或合并重复状态访问；先核对实际PYNQ版本实现和寄存器语义，再验证首次传输、复位、错误与超时路径。不能因为少读几个属性就预告5%整机收益。

接收缓存无效化、实际返回字节记录和DMA完成状态必须保留；DMA传参仍使用原PynqBuffer，不能传普通ndarray视图替代物理缓冲。出错需有界恢复，不删除timeout，也不能用无超时等待替换现有逻辑。状态读取合并后应优先处理错误，避免将错误状态误判成成功完成。

轮询、中断、原生扩展、直接寄存器驱动各有CPU占用、延迟与维护成本。先尝试有证据的局部改动，只有预计至少5%完整API收益且局部办法不足时再立项大改。若目标是减少CPU占用，应单独定义该指标，同时报告延迟与P95，不能只用平均API时间判断。

### P3：应用批量策略与更大批量性能，先补缺失数据

N=1继续保留较快的scalar路径。N=2/3等小批量应直接测“相同N个输入，用一次batch”与“连续N次scalar”的应用总时间，纳入凑批等待。已有输入集合与在线逐个到达是不同场景。

N=256/512已通过混合持续验证，下一步若业务需要更高吞吐，可补同口径独立API中位数、P95和原始重复测量，比较128/256/512的实际收益。不再把“验证到512”列为全新功能任务，也不把持续测试写成这两个规模已有正式A/B。

测量缓冲容量的影响：当前 `_exchange()` 对整个接收缓冲执行清零。扩容到512后再跑小N，与按N匹配容量的测试不完全相同；两边应使用相同容量策略，同时报告常驻内存/CMA、清零和缓存同步范围。现有匹配容量下清零仅约17–24 μs，单独优化不足5%，仅在更大常驻容量引入显著额外成本时重评。

进一步增大N之前先检查CMA可用性、分配失败清理、DMA长度与缓冲完整地址覆盖；16383仍只是协议/长度上限。在线系统记录真实到达时间和首样本/平均凑批等待，不能把所有输入已就绪的吞吐直接当成端到端响应能力。

### P4：有明确需求时扩展可靠性、能量或硬件资源实验

120秒连续测试已完成。若要长期部署，可按实际运行时长增加例如30–60分钟的混合负载、反复扩容/复用、故障后恢复和内存占用观察，先约定时长与通过条件。这是可靠性交付，不能计作API性能收益；具体预算是建议，不是新增用户硬约束。

资源、功率与PL延迟可以成为独立主目标，但当前没有新的硬件收益证据。若重开PL方向，保持全DSP、192路、单PL时钟，使用AX7020实际关键路径：父版最差路径是FC2 `first_pipe_reg[4]_rep` 到单累加器，数据延迟6.844 ns，其中布线5.768 ns。只改善7 ns下的WNS不算推理加速。

同周期数PL时间减5%需周期≤6.65 ns；该门槛不能直接转化为API减5%。当前时钟寄存器分频与驱动频率声明都需保持一致；不从历史Z2失败推断AX7020必败，也不因AX7020是-2器件就盲目扫频。能量实验应测真实负载下整板功率/每样本能量，资源下降和默认活动率估计不等于实测节能。
