日期：2026-10-06。基于最新 `quick_fc2_rom_pipe`，171 拍×4.30 ns=735.30 ns，启动间隔129拍=554.70 ns。只读取已有布线检查点生成诊断报告，并增加独立仿真观测；没有新综合、布局布线或修改候选 RTL。

## 结论

**当前频率的直接短板是 FC2 的 21 位累加路径；整体拍数和吞吐的主要限制在 FC1 的计算/输出安排；DSP 已用满，是扩展并行度的主要资源约束。** 三者不是同一个瓶颈。

数据路径延迟不等于最低可用时钟周期，还包含时钟偏斜、不确定度和setup要求。例如FC1数据路径3.341ns不能据此声称它可运行在3.341ns。

## 各层时刻：实际观测

独立诊断TB沿用原48请求数值检查，在posedge后1ps观测信号，记录第一个请求的相对拍数：

| 事件 | 相对拍数 |
|---|---:|
| 接收start | 0 |
| FC1第一个输出 | 19 |
| ready重新有效 | 128 |
| FC1最后一个输出 | 146 |
| FC2第一组4个输出 | 154 |
| FC2最后一组4个输出 | 161 |
| FC3第一个输出 | 170 |
| FC3第二个输出、全网done | 171 |

原TB持续请求的实际启动间隔仍为129拍；ready在第128拍恢复不等于TB会在同一拍再次启动。诊断仿真继续检查48个请求、7776项输出/地址，错误0。

FC1最后输出时已到146/171≈85.4%的端到端时间；之后尾部25拍≈14.6%。这并非三层独立耗时之和：FC2在FC1逐个输出时已持续接收和累加，层间存在重叠。

FC1输出128个结果，从19拍到146拍连续每拍1个，占128个输出时隙。当前输入计算发射也为128拍，因此两个环节都与128拍尺度有关。仅增加乘法并行度，而继续每拍只输出1个FC1结果，不能自动得到完整网络拍数上的显著收益。若要缩短这段，必须连同FC1结果打包/输出接口、FC2接收与累加方式共同预算。

FC2现有每拍接收1个FC1输出，在同拍对32个输出通道更新；若改成每拍接收2个或更多，需要额外乘法吞吐、相应权重带宽和累加组织。不能只把顶层接口加宽。

## 资源限制

全网DSP220/220=100%，LUT15734/53200≈29.6%，FF35596/106400≈33.5%，BRAM68/140≈48.6%。FC1占200个DSP（90.9%）、约87.9%的LUT、94.0%的FF和94.1%的BRAM。

因此“资源满了”主要指DSP，没有证据说整个芯片逻辑已耗尽。但空余LUT/FF不能直接转换成可用高速乘法，布局局部密度和布线仍可能约束扩展。之前512路方案的CARRY4容量/布局失败也说明只看总LUT百分比不够。

没有采集功耗或开关活动，不能据本报告判断电功耗、热瓶颈或每个DSP的实际利用率。

## 建议研究顺序

1. **先解释FC2累加网络为何形成当前长链。** 对照首项偏置、持续反馈累加、末项snapshot的实际网表，评估是否可改写成更短的数据路径。此处有逐拍反馈，普通“加一级寄存器”会改变计算依赖；如考虑交错累加或分段结果，必须重算数值、合并延迟和资源。
2. **再预算FC1输出/FC2接收的联动方案。** 先画每拍计算和输出表，估计减少输出时隙能否兑现为端到端收益；把DSP已用满、权重带宽、FC2额外乘法和累加成本算进去。
3. **同步留意FC1近关键路径。** 当前FC1已经有31条路径进入最差100条，且其最差路径约73.6%是布线，不能期待只改FC2一直提高频率。

本报告没有实施以上结构变化。按用户要求先诊断自身，下一次实验应围绕这些证据设定目标，继续执行先预算、收益不足时停止的约束。
