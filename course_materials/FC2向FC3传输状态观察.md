# FC2向FC3传输状态观察

2026-10-06，针对最新 `quick_fc2_rom_pipe`，在4.30ns时钟下增加独立TB观测。没有改变计算RTL，没有运行新综合或布线。第一个请求的start记为第0拍。

| FC3有效活动 | 拍数 | 说明 |
|---|---|---|
| 接收输入 | 155–162 | 连续8拍，每拍4个数，共32个输入；组地址0–7 |
| DSP乘法结果更新 | 157–164 | 4个配对乘法DSP，每组产生8项乘积，分别用于两个输出 |
| 乘积寄存 | 158–165 | 保存乘积并对齐有效标志 |

| 四项求和 | 160–167 | 合并两对结果 |
| 累加器更新 | 161–168 | 连续8拍，首组加偏置，后续组累加 |
| 读取结果 | 169–170 | 依次读取两个输出通道 |
| 输出 | 170–171 | 第171拍done |

这些窗口彼此重叠。第161拍FC3已经开始累加，此时仍接收第7组（组索引6）；第162拍接收最后一组（索引7）。第163–168拍输入有效标志已撤销，但FC3仍在处理流水中的有效数据，不能称为空闲。

FC2在第154–161拍时钟沿之后更新输出，FC3在下一次时钟沿即第155–162拍采样，因此两份观察相差1拍；这是同步寄存器传递的时间口径差异。

跨请求，FC3每129拍收到一次8拍突发输入，有效输入拍占比约6.2%；整个有效流水和输出活动窗口比8拍长。不能将6.2%解释为整个FC3的硬件利用率或功耗效率。无效周期的某些数据寄存器和乘法表达式仍更新，观察的标志表示有效工作而非时钟门控。

结论：FC3能连续接收FC2的输出，没有额外接收空档；计算在输入尚未收完时就开始。FC3不是当前吞吐瓶颈，但其流水排空和结果输出构成网络尾部延迟。
