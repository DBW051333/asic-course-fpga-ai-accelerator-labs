## 2. 操作记录

### 操作 1：保存基线

1. 在修改 RTL 前复制原工程，保存 `fc.v`、`fc_top.v`、`adder_tree.v` 和 `tb_fc_top.v` 到 `optimization_report/baseline/`。
2. 打开原工程的综合结果，导出 `timing_synth_full.rpt` 与 `utilization_synth_full.rpt`。
3. 对原工程运行至 `route_design`，导出 `timing_impl.rpt` 与 `utilization_impl.rpt`。这里使用的是布局布线后的结果，后面的方案也运行到同一步再比较。
4. 保存原有 XSim 日志 `xsim.log`，其中显示 128 个输出与 `fc1.txt` 全部匹配。

起点时的最差综合路径从一个 `channel_accum` 寄存器穿过通道选择与 32 位累加逻辑，到另一个 `channel_accum` 寄存器。因此先处理通道累加器，比直接给加法树或乘法器增加流水更有依据。

### 操作 2：把 128 个通道累加器改成一个

修改 `fc.v`，仅改变暂存中间和的方式：

```verilog
// 原设计
reg [31:0] channel_accum [0:127];
// 优化后
reg [31:0] channel_accum;
```
  
原控制顺序对每个输出通道连续处理 `group_idx=0,1,2,3`。第 0 组直接写入累加器，后 3 组依次相加；完成一个通道后，下一通道的第 0 组覆盖旧值。加偏置阶段也改为读取这个单一累加器。乘法器数目、RAM 内容、偏置、ReLU、输出格式和控制流水线级数均未改变。最终代码在 `fc.v` 第 41 行和第 154–194 行。

### 操作 3：用实际 Vivado IP 验证功能

在工程副本中运行 Vivado 2025.2 行为仿真，仿真顶层为 `tb_fc_top`，运行时间设为 6000 ns：

```tcl
open_project /home/ding/vivado_project/Lab4_optimized/Lab4.xpr
set_property xsim.simulate.runtime {6000ns} [get_filesets sim_1]
launch_simulation -mode behavioral
```

使用的是工程中的 BRAM 和 8 位有符号乘法器 IP 仿真模型。最终工程再次运行的日志为 `optimization_report/single_accumulator/xsim_final.log`，结果为 `PASS: all 128 FC outputs match fc1.txt`。基线与最终方案的测试平台都在 5345 ns 结束，表明这项优化没有增加本次计算的流水线周期数。

### 操作 4：综合并比较资源

在优化工程中重新运行综合，打开综合结果后导出时序与资源报告：

原工程和优化工程均在 `open_run synth_1` 后统计完整设计，因此 BRAM、DSP IP 都计入资源。原工程的完整报告在 `optimization_report/baseline/`，优化方案在 `optimization_report/single_accumulator/`。

优化工程最终交付目录中的 `timing_impl_final.rpt` 和 `utilization_impl_final.rpt` 是重新打开交付工程后核对的报告。

### 操作 6：试验拆分加法树，最后未采用

单累加器方案的综合最差路径移到了加法树 `stage1` 到 `stage2`。因此另外试过把原来第二级的三级串联加法拆成两级流水，并将 `group_idx`、输出地址、写使能和偏置延迟链同步延后 1 个周期。该试验版的源文件、XSim 日志以及综合和布局布线报告都在 `optimization_report/split_adder/`。XSim 的 128 个输出全部正确，但完成时间从 5345 ns 增至 5355 ns。

综合 WNS 从单累加器方案的 +4.038 ns 提高到 +5.614 ns；布线后 WNS 却从 +2.602 ns 变为 +2.473 ns，寄存器数增加 161。布线后最差路径转到权重地址寄存器至权重 RAM。因此没有把这项改动放入最终工程。

## 3. 测量结果

| 方案 | XSim 输出 | 综合 LUT | 综合寄存器 | 综合 WNS | 布线后 LUT | 布线后寄存器 | 布线后 WNS | 布线后 WHS | 仿真结束时刻 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 原设计 | 128/128 | 4591 | 7081 | +3.674 ns | 4587 | 7061 | +0.542 ns | +0.091 ns | 5345 ns |
| 单累加器，最终采用 | 128/128 | 2273 | 2976 | +4.038 ns | 2273 | 2944 | +2.602 ns | +0.018 ns | 5345 ns |
| 单累加器＋拆分加法树，未采用 | 128/128 | 2273 | 3137 | +5.614 ns | 2273 | 3105 | +2.473 ns | +0.099 ns | 5355 ns |

与原设计相比，最终方案在布线后少用 2314 个 LUT（约 50.4%）和 4117 个寄存器（约 58.3%），WNS 增加 2.060 ns。三个方案的 DSP 数都是 128，BRAM Tile 数都是 29.5。

## 4. 其他 PPT 优化点的处理决定

- **乘法器增加流水级、CSA 加法树**：当前 10 ns 目标已通过；最终方案布线后的最差路径在加法树，但简单拆分加法树并未改善最终 WNS。没有在缺少收益证据时继续增加级数。
- **共享乘法器、128 路改 64 路**：随后已做两组独立工程实测，包括保留原 RAM 布局、以及把 RAM 改为 512 位字宽。后者的 DSP 从 128 降到 64，LUT 从 2273 降到 1189，10 ns 时序仍通过；单次完整计算时间从 5.265 µs 增至 10.385 µs。操作过程和全部指标见同目录的 `并行度对比报告.md`。本工程仍保留 128 路方案，作为低延迟版本。
- **数据与控制对齐、流水线利用率**：最终采用方案没有增加流水级；未采用的拆分加法树试验同步调整了控制信号和偏置延迟链，并用 XSim 验证输出。
